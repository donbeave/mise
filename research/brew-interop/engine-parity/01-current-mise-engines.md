# 01 — Current mise Brew bootstrap engines

Questions: On latest `jdx/mise` main, what capabilities and semantics are implemented by system-package engines `brew:` and `brew-cask:` when driven by `mise bootstrap`, including entrypoints, requests, metadata, dependency closure, installation, receipts, state, ownership, lifecycle, platform behavior, sources, upgrades, pruning, uninstall, and failure boundaries?

Method: codebase read of https://github.com/jdx/mise @ `6f52dcdf99e282ef7a7db68c81301fa4618d0f79` (depth-1 clone; commit independently confirmed as `refs/heads/main` with `git ls-remote` on 2026-08-22).

## Findings

### What public paths exercise these engines?

- Bare `mise bootstrap` loads configured packages, runs `pre-packages`, selects non-plugin managers, then calls the shared driver with `Action::Install`; `--update`, `--dry-run`, and confirmation policy are passed through. `post-packages` runs after built-in packages when no plugin-package phase remains. — `src/cli/bootstrap.rs:123-165`, `src/cli/bootstrap.rs:1249-1289` (confidence: HIGH)
- Package-facing entrypoints are `apply`/`install`, `status`, `upgrade`, `prune`, `use`, formula-only `import`, and `brew tap`/`untap`. `use` writes config then invokes install; import scans linked formulae only; tap commands edit `[bootstrap.brew.taps]` and do not install a Homebrew tap checkout. — `src/cli/bootstrap.rs:795-841`, `src/cli/system/use.rs:14-24`, `src/cli/system/use.rs:81-145`, `src/cli/system/import.rs:31-53`, `src/cli/system/brew/mod.rs:7-29` (confidence: HIGH)
- Built-in managers expose a common side-effect-free `installed` query plus install/upgrade operations; default upgrade equals install. Both Brew managers are registered only on Unix and both report version-value pins unsupported. — `src/system/packages/mod.rs:122-215`, `src/system/packages/mod.rs:218-232`, `src/system/packages/brew/mod.rs:214-234`, `src/system/packages/brew/cask.rs:829-895` (confidence: HIGH)
- Shared driver installs missing, mismatched, or repairable packages; upgrades only present packages; skips per-package unavailable states; and filters unsatisfiable pins before calling either Brew engine. Config-driven unavailable managers are skipped unless `allow_unavailable_manager` is set; explicit package/manager requests fail. — `src/cli/system/driver.rs:41-55`, `src/cli/system/driver.rs:86-151`, `src/cli/system/driver.rs:152-180` (confidence: HIGH)

### How are requests, versions, taps, and platform selectors represented?

- A request carries name, optional config-value version, and optional tap URL. Brew names remain opaque: `@17` is part of formula/cask name, while a non-`latest` TOML value becomes a status-only version pin that these engines cannot install. — `src/system/packages/mod.rs:20-38`, `src/system/mod.rs:351-405`, `src/system/mod.rs:591-605`, `src/system/mod.rs:1522-1524` (confidence: HIGH)
- Package TOML accepts `version`, `os`, and `adopt`; `os` matches OS or `os/arch`, with macOS/darwin and x64/arm64 aliases. Nonmatching entries are removed before manager resolution. — `src/system/mod.rs:138-179`, `src/system/mod.rs:186-233`, `src/system/mod.rs:591-630` (confidence: HIGH)
- `[bootstrap.brew.taps]` attaches URLs only to fully qualified non-official `owner/tap/name` requests for both managers. Conventional tap URL defaults to `https://github.com/<owner>/homebrew-<tap>.git`; configured values override by config precedence. — `src/system/mod.rs:418-430`, `src/system/mod.rs:1503-1519`, `src/system/mod.rs:1545-1558`, `src/system/packages/brew/maintenance.rs:85-95` (confidence: HIGH)
- `adopt` is cask-only. Global `[bootstrap.brew].adopt` supplies the default; per-package `adopt` overrides it; resulting manager options are a set of cask names. Supplying `adopt` to `brew:` only warns and is ignored. — `src/system/mod.rs:307-318`, `src/system/mod.rs:336-349`, `src/system/mod.rs:591-640` (confidence: HIGH)

### What metadata and dependency resolution does `brew:` implement?

- Core formula metadata comes from unauthenticated `https://formulae.brew.sh/api/formula/<name>.json`, cached only in memory for process lifetime. Parsed fields include aliases, stable version/revision, keg-only, runtime/build dependencies, bottle variations, source URLs/checksums, and pinned Ruby-source provenance. — `src/system/packages/brew/api.rs:1-47`, `src/system/packages/brew/api.rs:93-146`, `src/http.rs:693-703` (confidence: HIGH)
- Third-party formula requests read `api/formula/<formula>.json` from a conventional or configured GitHub raw base. Explicit `homebrew/core/name` normalizes to core. Non-GitHub configured URLs cannot form a raw base and fail; mise never falls back to invoking `brew`. — `src/system/packages/brew/api.rs:148-178`, `src/system/packages/brew/api.rs:212-243`, `src/system/packages/brew/mod.rs:299-358` (confidence: HIGH)
- Formula closure resolution canonicalizes aliases, applies dependency lists from the selected bottle-tag variation, includes runtime dependencies always, adds build dependencies only for source builds, and topologically orders dependencies first. Dependency cycles are deliberately broken rather than rejected. — `src/system/packages/brew/resolve.rs:37-59`, `src/system/packages/brew/resolve.rs:61-169`, `src/system/packages/brew/resolve.rs:171-234` (confidence: HIGH)
- A dependency of a tapped formula is tried against core first, then the parent tap; a requested tapped formula goes directly to tap metadata. Tap URL/tap identity propagate through tap-local dependency resolution. — `src/system/packages/brew/resolve.rs:99-160`, `src/system/packages/brew/resolve.rs:237-257` (confidence: HIGH)
- Formula aliases resolve for installation, but status checks the request spelling's `opt/<name>` record without metadata resolution. Install warns that an alias must be replaced by canonical name for status tracking. — `src/system/packages/brew/mod.rs:86-99`, `src/system/packages/brew/mod.rs:236-251`, `src/system/packages/brew/mod.rs:314-340` (confidence: HIGH)

### What does `brew:` install or pour?

- Engine availability is arm64 macOS plus x86_64/arm64 Linux. Canonical prefix is `/opt/homebrew` on macOS and `/home/linuxbrew/.linuxbrew` on Linux; source/pour code does not shell out to `brew`. — `src/system/packages/brew/mod.rs:1-18`, `src/system/packages/brew/mod.rs:220-230`, `src/system/packages/brew/prefix.rs:1-45` (confidence: HIGH)
- Prefix bootstrap creates Homebrew-shaped directories. Depending on whether mise is running normally, as root, or through sudo, a new or non-writable existing prefix can trigger recursive `chown -R` through mise's sudo policy; missing subdirectories inside an otherwise usable prefix are created without rewriting ownership. — `src/system/packages/brew/prefix.rs:11-32`, `src/system/packages/brew/prefix.rs:125-165`, `src/system/packages/brew/prefix.rs:167-243` (confidence: HIGH)
- Bottle selection prefers newest compatible arm64 macOS tag not newer than host, then `all`; Linux selects architecture tag then `all`. Failure to read macOS version leaves only `all`. — `src/system/packages/brew/tag.rs:1-72` (confidence: HIGH)
- Bottle path downloads declared URL into mise cache, verifies SHA-256, extracts into a temporary rack directory, relocates text plus Mach-O/ELF linkage, re-signs changed Mach-O files, writes receipt, renames into Cellar, then links. — `src/system/packages/brew/fetch.rs:12-38`, `src/system/packages/brew/pour.rs:191-270` (confidence: HIGH)
- Public linking covers `bin`, `sbin`, `include`, `lib`, `share`, `Frameworks`; `etc` and `var` are omitted. Keg-only formulae receive only `opt/<name>`. All conflicts are collected before links are changed; non-symlink foreign targets are refused; partial link creation restores replaced symlinks and removes new ones. — `src/system/packages/brew/pour.rs:16-19`, `src/system/packages/brew/pour.rs:400-416`, `src/system/packages/brew/pour.rs:546-644` (confidence: HIGH)
- Existing symlinks into Cellar/opt, including directory-level links, are treated as Brew-owned and replaceable. This permits relinking over either mise- or Homebrew-created formula links while refusing ordinary files/directories. — `src/system/packages/brew/pour.rs:400-433`, `src/system/packages/brew/pour.rs:473-543`, `src/system/packages/brew/pour.rs:594-625` (confidence: HIGH)
- No usable bottle triggers source build, not immediate rejection. Before any prefix work for that batch, mise requires stable archive URL/checksum, supported download strategy, Ruby source path/checksum, and tap git head. — `src/system/packages/brew/mod.rs:112-145`, `src/system/packages/brew/source.rs:33-94` (confidence: HIGH)
- Source build provisions mise-managed Ruby, fetches checksum-pinned formula Ruby at API snapshot commit, verifies source archive, evaluates in-repo Formula DSL shim, runs both `install` and `post_install`, writes same receipt shape, and links resulting keg. Unknown install-time helpers fail; class-level unknown metadata only warns. — `src/system/packages/brew/source.rs:96-177`, `src/system/packages/brew/source.rs:180-240`, `src/system/packages/brew/shim.rb:667-677`, `src/system/packages/brew/shim.rb:850-910` (confidence: HIGH)
- Formula shim supports formula commands, resources, and patches; formula `etc` and `var` address shared prefix outside keg. On source-build failure Rust removes keg, but no transaction covers shared-prefix writes or commands already executed by formula code. — `src/system/packages/brew/shim.rb:373-474`, `src/system/packages/brew/shim.rb:713-739`, `src/system/packages/brew/source.rs:125-176` (confidence: HIGH)
- Bottle pours do not evaluate formula Ruby or invoke `post_install`; only source-build shim does. Search method `rg -n -i 'openssl|ca-cert|cert.pem|trust store|post_install' src/system/packages/brew` found no OpenSSL/CA/default-trust branch, only generic shim `post_install`. — `src/system/packages/brew/mod.rs:175-192`, `src/system/packages/brew/shim.rb:854-898` (confidence: HIGH)
- Formula receipt is `INSTALL_RECEIPT.json` with bottle/source flag, requested/dependency ownership bits, aliases, direct runtime dependency versions, tap, arch, and changed files. Code labels it Brew-compatible; static read proves shape, not live compatibility with a separately installed Homebrew version. — `src/system/packages/brew/pour.rs:299-375` (confidence: HIGH for written shape; MED for external compatibility claim)

### What are `brew:` installed, health, upgrade, ownership, and prune semantics?

- Formula installed state is driven only by an existing keg reached from active `opt/<name>`. It reports version mismatch before repair; requested `17.5` accepts active `17.5_1`. It does not inspect metadata, receipt, dependency closure, keg contents, public links generally, or post-install effects. — `src/system/packages/brew/pour.rs:31-53`, `src/system/packages/brew/mod.rs:236-251`, `src/system/packages/brew/mod.rs:323-341` (confidence: HIGH)
- Repair is narrow: reconstruct missing/dangling `opt` from valid linked-keg record, or missing linked-keg record from valid `opt` plus public links. Keg-only formulae do not require linked-keg record. — `src/system/packages/brew/pour.rs:45-109`, `src/system/packages/brew/mod.rs:57-74` (confidence: HIGH)
- Presence ownership is intentionally not distinguished: a valid active keg poured by real Homebrew satisfies `installed`; upgrades may replace Brew-owned active links. Conversely, mise writes request/dependency bits into receipts for later import/prune classification, but those bits do not gate status or mutation. — `src/system/packages/brew/mod.rs:236-251`, `src/system/packages/brew/pour.rs:400-433`, `src/system/packages/brew/pour.rs:336-370`, `src/system/packages/brew/maintenance.rs:97-142` (confidence: HIGH)
- Upgrade resolves current metadata and pours/builds any closure version not currently active, then relinks it. No code removes inactive older keg directories during upgrade; `installed_versions` explicitly retains all version directories, with active first. — `src/system/packages/brew/mod.rs:276-295`, `src/system/packages/brew/mod.rs:100-110`, `src/system/packages/brew/pour.rs:166-189`, `src/system/packages/brew/pour.rs:607-625` (confidence: HIGH)
- Formula prune computes keep-set as dependency closure of current plus trusted tracked configs, then enumerates every active `opt` link and removes each active keg not kept. Enumeration accepts absent receipts and does not require mise ownership; therefore active foreign Homebrew formulae are candidates. Only links resolving into target keg are removed. — `src/cli/system/prune.rs:59-93`, `src/system/packages/brew/maintenance.rs:97-147`, `src/system/packages/brew/maintenance.rs:164-190`, `src/system/packages/brew/maintenance.rs:226-299` (confidence: HIGH)
- Formula prune sees active links only. Inactive old kegs left by upgrade are neither candidates nor removed; rack removal succeeds only when empty, so removing the active keg leaves any inactive versions in place. — `src/system/packages/brew/maintenance.rs:97-142`, `src/system/packages/brew/maintenance.rs:175-190`, `src/system/packages/brew/maintenance.rs:226-246`, `src/system/packages/brew/pour.rs:166-189`, `src/file.rs:228-238` (confidence: HIGH)
- No separate Brew uninstall entrypoint exists in bootstrap package commands; removal path is `packages prune`. Import is formula-only and defaults to active receipts with `installed_on_request=true`, while `--all` includes dependencies and receipt-less active kegs. — `src/cli/bootstrap.rs:830-841`, `src/cli/system/import.rs:31-53`, `src/system/packages/brew/maintenance.rs:97-142` (confidence: HIGH)

### What are `brew-cask:` receipt, state, ownership, adoption, and upgrade semantics?

- Successful install writes durable `.mise-cask.toml` schema 3 inside versioned Caskroom. Receipt records version, auto-update mode, metadata-only apps, categorized targets, pkg IDs, target fingerprints, flight directories, and prune safety/blocker. — `src/system/packages/brew/cask.rs:273-307`, `src/system/packages/brew/cask.rs:6644-6720`, `src/system/packages/brew/cask.rs:6886-6910` (confidence: HIGH)
- Status first fetches current upstream metadata and parses artifacts/platform support, then requires exactly one Caskroom version, no pending transaction journal, and a mise receipt. Schema 2/3 health requires receipt target presence plus pkg receipts; dependency closure is not checked and current API artifacts are unused in health. — `src/system/packages/brew/cask.rs:847-875`, `src/system/packages/brew/cask.rs:6380-6408`, `src/system/packages/brew/cask.rs:6557-6607` (confidence: HIGH)
- Status presence is deliberately weaker than content identity: file/directory contents may drift and remain installed; symlinks must keep recorded destination and resolve. Full fingerprints are reserved for adoption/prune safety. — `src/system/packages/brew/cask.rs:6723-6784` (confidence: HIGH)
- A Homebrew `.metadata` directory is treated as foreign ownership. Status still reports such cask missing because no mise receipt; subsequent apply refuses mutation, checking both before download and again under Caskroom lock. Recognition therefore does not transfer ownership. — `src/system/packages/brew/cask.rs:428-447`, `src/system/packages/brew/cask.rs:529-543`, `src/system/packages/brew/cask.rs:6410-6415`, `src/system/packages/brew/cask.rs:6557-6607` (confidence: HIGH)
- Explicit adoption applies only when no mise-installed version exists. For non-auto-update casks, existing app bundles must fingerprint-identically match staged artifacts before metadata-only ownership is recorded. For `auto_updates` casks, identity verification is skipped and an existing app path can be adopted as metadata-only. — `src/system/packages/brew/cask.rs:523-528`, `src/system/packages/brew/cask.rs:600-613`, `src/system/packages/brew/cask.rs:1255-1342` (confidence: HIGH)
- Without adoption, existing app bundles are atomically replaced. Binary/font/completion activation starts a link transaction: existing targets are renamed to backups, restored on failure, then backups are deleted on commit; completion targets additionally reject unrelated existing non-symlinks/links, but binary and font paths have no equivalent foreign-ownership gate. — `src/system/packages/brew/cask.rs:1255-1325`, `src/system/packages/brew/cask.rs:1351-1439`, `src/system/packages/brew/cask.rs:655-699`, `src/system/packages/brew/cask.rs:4137-4165`, `src/system/packages/brew/cask.rs:7434-7518` (confidence: HIGH)
- Non-auto-update upgrade reinstalls when receipt version differs from current API version, activates the new version, removes stale Caskroom versions, and removes obsolete recorded links/artifacts. `auto_updates` returns already installed regardless of receipt/API version, so explicit upgrade does not refresh the artifact. — `src/system/packages/brew/cask.rs:442-447`, `src/system/packages/brew/cask.rs:538-543`, `src/system/packages/brew/cask.rs:701-715`, `src/system/packages/brew/cask.rs:7558-7571`, `src/system/packages/brew/cask.rs:893-895` (confidence: HIGH)

### What prune/uninstall behavior does `brew-cask:` implement?

- Cask prune keep-set contains canonical tokens of configured current/tracked requests only; it does not compute cask dependency closure. A mise-owned cask installed only as another cask's dependency can therefore become an unconfigured prune candidate. — `src/cli/system/prune.rs:99-139`, `src/system/packages/brew/cask.rs:6913-6919` (confidence: HIGH)
- Candidate discovery refuses Homebrew-owned tokens, missing/unreadable receipt, multiple versions, pending transaction, pre-v3 receipt, `prune_safe=false`, incomplete ownership index, or targets shared with another cask. — `src/system/packages/brew/cask.rs:6921-7146` (confidence: HIGH)
- Receipt is prune-safe only when install lacks pkg, installer, command-wrapper, generic, install lifecycle, uninstall lifecycle, and metadata-only app effects. Pkg removal and uninstall hooks are not implemented; their presence blocks direct pruning. — `src/system/packages/brew/cask.rs:6609-6641`, `src/system/packages/brew/cask.rs:6680-6716` (confidence: HIGH)
- Apply-prune locks Caskroom, revalidates receipt, fingerprints, allowed target roots, and cross-cask claims, journals removals, deletes exact recorded targets, then removes version/token directories. If any recorded target changed, the whole cask candidate is skipped. — `src/system/packages/brew/cask.rs:7149-7197`, `src/system/packages/brew/cask.rs:7211-7245`, `src/system/packages/brew/cask.rs:7248-7368` (confidence: HIGH)
- No independent cask uninstall command exists; `packages prune --manager brew-cask` is sole built-in removal path and is intentionally unavailable for casks needing uninstall/lifecycle behavior. — `src/cli/bootstrap.rs:830-841`, `src/cli/system/prune.rs:22-52`, `src/system/packages/brew/cask.rs:6609-6641` (confidence: HIGH)

### How do platform and failure boundaries behave?

- `brew-cask` manager reports available on macOS and Linux. Linux per-package validation permits only font-only casks without apps, binaries, installers, generic/completion artifacts, structured lifecycle, or Ruby lifecycle; status returns `Unavailable`, while explicit apply fails and config-driven apply skips. — `src/system/packages/brew/cask.rs:835-845`, `src/system/packages/brew/cask.rs:5030-5062`, `src/cli/system/driver.rs:45-55`, `src/cli/system/driver.rs:109-123` (confidence: HIGH)
- Cask manager has no architecture gate and parsed `depends_on` omits macOS version/architecture constraints. Host/arch branching exists only where artifact metadata or lifecycle Ruby explicitly encodes supported conditionals. — `src/system/packages/brew/cask.rs:85-97`, `src/system/packages/brew/cask.rs:835-841`, `src/system/packages/brew/cask_shim.rb:55-145`, `src/system/packages/brew/cask_shim.rb:302-312` (confidence: HIGH)
- Formula install is sequential over dependency-first closure. Each completed keg remains if a later formula fails; failed current bottle/source keg is removed after link/build failure, but batch has no global rollback. — `src/system/packages/brew/mod.rs:166-210`, `src/system/packages/brew/pour.rs:251-269`, `src/system/packages/brew/source.rs:125-176` (confidence: HIGH)
- Cask dependency installs occur before root transaction. For root cask, Caskroom/link/structured external-target changes have backup/rollback machinery, but pkg installers, script installers, lifecycle commands, process termination, and other command side effects are not generally reversible. A pending durable journal makes status missing after incomplete transaction. — `src/system/packages/brew/cask.rs:458-487`, `src/system/packages/brew/cask.rs:550-699`, `src/system/packages/brew/cask.rs:3470-3477`, `src/system/packages/brew/cask.rs:6571-6573`, `src/system/packages/brew/cask.rs:6833-6899` (confidence: HIGH)
- Both cask artifact parsing and Linux-support validation happen before prefix bootstrap/download, preventing mutation for statically unsupported artifact or platform shapes. Unsupported behavior reached only inside a Ruby/structured command can fail later, after earlier lifecycle actions. — `src/system/packages/brew/cask.rs:428-435`, `src/system/packages/brew/cask.rs:488-524`, `src/system/packages/brew/cask.rs:571-642`, `src/system/packages/brew/cask_shim.rb:314-345`, `src/system/packages/brew/cask_shim.rb:359-410` (confidence: HIGH)
- `--update` reaches `InstallOpts`, but neither Brew engine reads `opts.update`; both metadata clients fetch through process-memory-only `json_cached`. A new CLI process fetches again, so update flag adds no Brew-specific refresh action. — `src/cli/system/driver.rs:82-85`, `src/system/packages/brew/mod.rs:254-295`, `src/system/packages/brew/cask.rs:370-407`, `src/http.rs:693-703` (confidence: HIGH)

## Dead ends and contradictions

- CLI prose says formula upgrade “replaces the old keg,” but current upgrade only relinks current version and leaves older Cellar directories. Formula prune enumerates active `opt` links, so those inactive versions survive prune too. — `src/cli/system/upgrade.rs:10-16`, `src/system/packages/brew/pour.rs:166-189`, `src/system/packages/brew/maintenance.rs:97-142` (confidence: HIGH)
- Current formula health conflicts with lifecycle-aware health premise: bottle path never executes formula `post_install`, and installed state has no lifecycle-effect record/check. Source builds execute `post_install`, but status still checks only active-link state. — `src/system/packages/brew/mod.rs:175-192`, `src/system/packages/brew/shim.rb:886-902`, `src/system/packages/brew/mod.rs:236-251` (confidence: HIGH)
- Current main does use Ruby shims and ambient helpers: formula source build executes formula Ruby with `system`; cask hook selection tries `brew ruby` and ambient `ruby`; script installers extend ambient `PATH`.
